# 파인튜닝

파인튜닝(Fine-tuning)은 사전 학습된 LLM을 자신의 데이터로 추가 학습시켜, 특정 스타일·형식·도메인에 맞게 조정하는 것입니다.

## 언제 파인튜닝을 쓰나

| 상황 | 적합한 방법 |
|------|-------------|
| 최신 정보·사내 문서를 답변에 반영하고 싶다 | [RAG](rag.md) |
| 특정 출력 형식·말투를 일관되게 강제하고 싶다 | 파인튜닝 |
| 프롬프트가 너무 길어져 비용이 부담된다 | 파인튜닝 (지시를 모델에 내재화) |
| 도메인 특화 용어·패턴을 깊게 이해시키고 싶다 | 파인튜닝 + RAG 병행 |
| 일반적인 작업 몇 가지를 시키고 싶다 | 프롬프트 엔지니어링만으로 충분 |

핵심 원칙: **지식 주입은 RAG, 행동 교정은 파인튜닝**. 대부분의 경우 프롬프트 개선과 RAG를 먼저 시도하고, 그래도 안 될 때 파인튜닝을 검토하는 것이 비용 효율적입니다.

## 주요 방식

- **전체 파인튜닝 (Full fine-tuning)**: 모델의 모든 파라미터를 업데이트. 효과가 크지만 GPU 비용이 매우 큽니다.
- **LoRA / QLoRA**: 원본 파라미터는 고정하고 작은 어댑터 행렬만 학습. 적은 자원으로 전체 파인튜닝에 근접한 효과를 내서 오픈소스 모델 파인튜닝의 사실상 표준입니다.
- **API 파인튜닝**: 상용 모델 제공사가 제공하는 관리형 파인튜닝. 인프라 걱정 없이 데이터만 업로드하면 됩니다.

## 데이터 준비

품질이 전부입니다. 보통 아래 형식의 대화 예시를 수백~수만 건 준비합니다.

```json
{"messages": [
  {"role": "system", "content": "당신은 고객 지원 상담원입니다."},
  {"role": "user", "content": "환불은 어떻게 하나요?"},
  {"role": "assistant", "content": "주문 내역 페이지에서..."}
]}
```

- 실제 서비스에서 원하는 "모범 답변"만 담으세요. 나쁜 예시가 섞이면 그대로 배웁니다.
- 다양한 케이스를 고르게 포함하고, 일부는 평가용으로 떼어두세요.

## 주의점

- **과적합**: 데이터가 적거나 편향되면 일반 능력이 오히려 떨어질 수 있습니다.
- **유지보수**: 요구사항이 바뀔 때마다 재학습이 필요합니다. RAG보다 갱신 비용이 큽니다.
- **평가 없이는 진행 금지**: 학습 전후를 같은 평가 셋으로 비교해야 개선 여부를 알 수 있습니다.
